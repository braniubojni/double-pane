# Spec: Checksum tool V1

Status: draft
Out of scope: SHA-1, CRC32, `sha256sum` file import, hashing directories as a single digest, remote MEGA (MEGA already has `MEGAManager.HashFile` for the duplicate finder), auto-hash on every copy

Cursor: implement this spec only. Read `internal/AGENTS.md` and `frontend/AGENTS.md` first.

## Goal

Hash selected files (MD5, SHA-256, SHA-512) and, after a copy, optionally check that the destination bytes match the source.

## Current behavior

`filesystem.HashFile` streams SHA-256 only (`crypto/sha256`, `io.Copy`, context cancel closes the reader). The duplicate finder uses it. Nothing in the file pane shows a digest. `FileService.Copy` emits `transfer:progress` / `transfer:done` and does not hash.

## API

Generalize hashing. Keep `HashFile` as SHA-256 so the duplicate finder does not change.

```go
func HashFileAlgo(ctx context.Context, path, algo string) (string, error)
```

`algo` is `md5`, `sha256`, or `sha512` (`crypto/md5`, `crypto/sha256`, `crypto/sha512`). Hex lowercase. Unknown algo is an error. Directories are an error. Symlinks: hash the target file (`os.Open` follows), same as `HashFile` today.

`FileService.HashPaths(jobID string, paths []string, algo string) error`

Streams `hash:hit` (`path`, `algo`, `digest`) and `hash:done` (`jobID`, `error`). One file failure sets that row's error and continues. `CancelJob` stops the rest. Local paths use `HashFileAlgo`. `ssh://` and `smb://` use `remoteBackend.OpenRead` and `filesystem.HashReader`. `mega://` returns an error from this API (duplicate-finder MEGA hashing stays on its own path).

Verify after copy is not inside `Copy`. The UI calls `HashPaths` twice (source list, then dest list) and compares digests by basename. Different relative names are not paired.

## UX

Context menu "Checksum…" when the selection is files only. Dialog `data-testid="dialog-checksum"`: algo radio (default SHA-256), a row per file with digest and a copy button. `data-testid="checksum-digest"`.

After a successful local or SSH/SMB copy, the existing success snack gets an action "Verify checksums" (`data-testid="btn-verify-copy"`) when the copy was files (not a directory tree). Click runs SHA-256 on sources and dests and shows a dialog: match count, or the first mismatch path. Directory copies do not offer it (a tree hash is out of scope).

No new shortcut default. Command palette id `checksum`.

## Tests

`go test` in `filesystem`:

- same bytes → same sha256 as `HashFile`, and a stable md5 fixture (`d41d8cd98f00b204e9800998ecf8427e` for empty)
- unknown algo errors
- cancel returns `context.Canceled` and does not return a digest

## Must not

- Buffer the whole file.
- Change duplicate-finder hash ids (`sha256:` prefixes in that feature stay SHA-256).
