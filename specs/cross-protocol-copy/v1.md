# Spec: Copy and move between SSH and SMB V1

Status: draft
Out of scope: MEGA as either side, FTP, two different SSH hosts (already `cross-host copy not supported` in `internal/remote/ssh.go`), two SMB servers, pause/resume (SFTP pause stays in `specs/sftp-transfer-control/v1.md`)

Cursor: implement this spec only. Read `internal/AGENTS.md` first.

## Current behavior

`FileService` classifies a transfer in one place (around the `cross-protocol copy not supported` returns in `file_service.go`):

- same scheme, both remote → within-host copy on that backend
- remote → local download, local → remote upload
- different schemes, or mixed selection → error `cross-protocol copy not supported`
- SSH `CopyWithin` also errors `cross-host copy not supported` when source and dest sessions differ (`ssh.go`, `smb_transfer.go`)

So a file on `ssh://` cannot be copied onto `smb://` in one action. The user can download to a local pane and upload, which is two jobs.

## Desired

One copy or move when every source is `ssh://` and the dest is `smb://`, or the reverse. Selection must be one scheme (the existing mixed-selection error stays).

Implement it in `FileService` as download to a temp directory, then upload, then delete the temp. Use the backends' existing `Download` and `Upload` (or `OpenRead` plus the upload writer if Download always targets a user-chosen folder — do not point Download at the user's pane). Temp dir is under `os.TempDir()` in a `double-pane-xfer-<jobID>` folder, mode `0o700`, removed on success, on error, and on `CancelJob`.

Progress: one job id, one `transfer:progress` / `transfer:done`. `bytesTotal` is `2 * sourceBytes` (the down and the up). `bytesDone` advances on both phases. Label kind stays `copy` or `move`.

Move: after the upload succeeds, `Delete` the sources on the source backend. If delete fails, the dest copy remains and the error says the source was not removed. Do not delete sources before the upload finishes.

Cancel during download: delete partial temp, do not upload. Cancel during upload: `CancelJob` on the upload and delete the partial dest the way that backend already does, then delete the temp.

Same-host SSH and same-server SMB copy are unchanged. Do not route them through temp.

## Tests

With fake or local stand-ins if the backends are hard to dial: a unit test on the classifier that ssh→smb is the new kind, not an error. An integration-style test with temp files if a fake `remoteBackend` can be injected — `FileService` does not have a public setter for backends today, so prefer testing the helper that performs temp download+upload with two `remoteBackend` fakes rather than opening sockets.

Assert temp dir is gone after success and after cancel.

## Must not

- Leave temp files on success.
- Copy SSH→MEGA or SMB→MEGA in this spec.
- Change `cross-host copy not supported` for two SSH hosts.
