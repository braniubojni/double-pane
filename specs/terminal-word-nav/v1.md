# Spec: Terminal word navigation V1

Status: draft
Out of scope: changing the user's zshrc, iTerm2 key-binding import, mouse selection, a second terminal widget

Cursor: implement this spec only. Read `frontend/AGENTS.md` first. The PTY stays `TerminalService` (`spawnLocalPTY` runs `$SHELL -l` or `/bin/zsh`).

## Current behavior

`frontend/src/widgets/terminal/hooks/useXterm.ts` constructs `@xterm/xterm` `Terminal` and sends every key through `term.onData` → `TerminalService.Write`. There is no `customKeyEventHandler` and no `macOptionIsMeta`. Option+Left/Right (Alt+Left/Right on Linux/Windows) therefore go out as the normal arrow sequences (`CSI D` / `CSI C`). zsh emacs mode does not treat those as word motions.

iTerm2's "Natural Text Editing" preset sends `ESC b` and `ESC f` for Option+Left and Option+Right. Zsh and bash emacs bindings already map those to `backward-word` and `forward-word`. During zsh completion, the same widgets move by word inside the line. The app does not implement completion; it only has to send the bytes the shell already understands.

`macOptionIsMeta` is the wrong switch for arrows: xterm prefixes ESC onto the CSI sequence (`ESC ESC [ D`), which is not `ESC b`.

## Desired

In `useXterm`, `term.attachCustomKeyEventHandler` (xterm's own handler, not a `window` listener):

- Alt+Left or Meta+Left (macOS Option is `altKey`): `term.input('\x1bb')` and return false so xterm does not also send the arrow.
- Alt+Right or Meta+Right: `term.input('\x1bf')` and return false.
- Shift held: do not handle (let xterm select or send the shifted arrow).
- Ctrl held: do not handle.
- Any other key: return true.

This covers Option+arrow on macOS and Alt+arrow elsewhere, including when a completion menu is open, because the shell receives `backward-word` / `forward-word` either way.

Do not write a termcap, do not run `bindkey` in the PTY, do not set `macOptionIsMeta`.

## Check

Manual, in the pane terminal, zsh:

- `echo one two three`, Option+Left moves to `two`, then `one`. Option+Right moves forward a word.
- Trigger completion (`cd ` + Tab on a path with several components, or type a partial word) and Option+Right moves one word of the command line, not one character.
- Plain Left/Right still move one character.
- Ctrl+Left/Right are unchanged from xterm's default.

No Playwright spec (PTY and Option are outside the e2e DOM). A unit test is optional; the handler can be a pure function `wordNavBytes(event) (string, bool)` tested for alt+left → `\x1bb`, alt+right → `\x1bf`, left without alt → not handled, alt+shift+left → not handled.

## Must not

- `document` or `window` listeners (`specs/no-dom-globals/v1.md`).
- `window.setTimeout` to focus the terminal. `term.focus()` in the existing effect stays.
