# Spec: clean dist/ before a PUBLISH=true build V1

Status: draft
Out of scope: cleaning dist/ on plain `task dist` (PUBLISH unset/false), cleaning bin/, changing SHA256SUMS generation logic itself

## Problem

`task dist VERSION=X.Y.Z PUBLISH=true` runs `dist:build` → `dist:archive` → `dist:maybe-publish` (`Taskfile.yml:285-345`). `dist:archive` only `rm -f`s the four filenames matching *this* `VERSION`/arch combo (`Taskfile.yml:379-382`) — it never touches unrelated files already sitting in `dist/` (a prior version's archives, a manual copy, a half-finished run). `dist:archive` then regenerates `dist/SHA256SUMS` by walking `dist/*.zip` / `dist/*.tar.gz` (`Taskfile.yml:420-467`), and `release:publish` uploads with `gh release create "$TAG" dist/*` (`Taskfile.yml:512`) — a plain glob, everything present goes up.

Net effect: stale artifacts from an earlier build (different version, leftover from an interrupted run, whatever) silently ride along into the new GitHub Release and into SHA256SUMS. The in-app updater trusts SHA256SUMS to verify what it downloads — a stale entry there for a file that doesn't match this release's tag is a correctness problem, not just clutter.

## Fix

When `PUBLISH=true`, empty `dist/` completely before anything gets built into it — not after, not "clean this version's files only." When `PUBLISH=false` (default, local `task dist` for testing a build), leave existing behavior alone: don't surprise someone doing an incremental local build by wiping artifacts they may still want.

`Taskfile.yml` — new internal task, next to `dist:maybe-publish`:

```yaml
  dist:maybe-clean:
    internal: true
    status:
      - '[ "{{.PUBLISH}}" != "true" ]'
    cmds:
      - rm -rf dist
      - mkdir -p dist
```

Wire it as the **first** cmd in `dist:` (`Taskfile.yml:306`, before the `defer: { task: docker:maybe-quit }` line) — it doesn't depend on Docker, so no reason to make it wait, and it must run before `dist:build`/`dist:archive` put anything new in `dist/`:

```yaml
    cmds:
      - task: dist:maybe-clean
        vars:
          PUBLISH: "{{.PUBLISH}}"
      - defer: { task: docker:maybe-quit }
      - task: docker:ensure
        ...
```

Same `status: '[ "{{.PUBLISH}}" != "true" ]'` skip pattern already used by `dist:maybe-publish` — consistent, no new mechanism introduced.

## Must not

- Wipe `dist/` on a plain `task dist` (no `PUBLISH`) — that's the local/manual-inspect path (`task release:publish` run separately afterward per the task's own `desc`), and people rely on being able to look at what a bare `task dist` produced.
- Move the clean into `dist:archive` — too late, `dist:build` would already be writing into a dir that still had old junk in it, and `dist:build` isn't where dist/ files land anyway (it writes to `bin/`, `dist:archive` fills `dist/`). Cleaning must happen before `dist:build` starts, not just before `dist:archive`.
- Delete `bin/` — out of scope, `dist:build` overwrites `bin/` outputs directly by path, no accumulation problem there.
- Add a confirmation prompt before deleting `dist/` — this is a build artifacts directory, not user data; existing `rm -f` in `dist:archive` already deletes without asking.

## Done when

- [ ] `dist/` has a stale file (e.g. `dist/old_1.0.0_darwin_arm64.zip`) → `task dist VERSION=2.0.0 PUBLISH=true` → `dist/` after the run contains only `2.0.0` artifacts + `SHA256SUMS`, stale file gone
- [ ] same stale-file setup → `task dist VERSION=2.0.0` (PUBLISH unset) → stale file still present after the run, untouched
- [ ] `dist:maybe-clean` runs before `docker:ensure`/`dist:build` in the `dist:` cmds list (ordering, not just presence)
