# Spec: Plugin points — decision V1

Status: deferred
Out of scope: a plugin loader, WASM, Lua, subprocess plugins, a marketplace, signing

Cursor: do not implement a plugin system from this file. Read it so a later change does not add one casually.

## Why this file exists

The backlog says plugin/extension points are low priority and only worth it if long-term extensibility is actually needed. Nothing in the app loads third-party code today. `main.go` registers a fixed set of Wails services (`FileService`, `SettingsService`, `BookmarkService`, `TerminalService`, `ConnectionService`, `UpdateService`, `GitService`, `PortService`, `AIUsageService`).

## What already extends behavior

These are the extension points that exist. New features should use them instead of a plugin API.

| Need | Use |
| ---- | --- |
| Another command | `config.ShortcutCatalog` + `runShortcutAction` |
| Another context-menu row | `FileContextMenu.tsx` items |
| Another file action | `FileService` method + a toolbar hook |
| Open a file in another app | `ListOpenWithApps` / `OpenWith` (`internal/config/openwith_*.go`) |
| Another remote scheme | `remoteBackend` + `backendFor` (see `specs/ftp/v1.md`) |

## When a plugin host would be justified

All of these, not one of them:

- A feature the core team will not maintain (a protocol or a previewer) has a named external author.
- It cannot be done with Open With or a catalog command.
- The host can crash a bad plugin without taking down the file walk.

Until then, do not add `plugins/`, a manifest format, or dynamic `import()` of user paths.

## If that day comes

A later spec (not this one) would start from one hook only: a command-palette row that runs an allowed executable with the selected paths as arguments, no in-process Go plugin. This file does not specify that executable protocol.

## Must not

- Add a dependency "so plugins are possible later".
- Refactor services into interfaces whose only caller is the future host.
