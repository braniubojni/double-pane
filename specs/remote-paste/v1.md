# Spec: Paste into a remote directory V1

Status: draft
Out of scope: putting remote files on the OS clipboard, Finder pasting an `ssh://` URL, changing in-app Copy (Mod+Shift+C already transfers to the other pane, including remote), pause/resume (that is `specs/sftp-transfer-control/v1.md`), archive destinations, trash destinations

Cursor: implement this spec only. Read `internal/AGENTS.md` and `frontend/AGENTS.md` first.

## Goal

Mod+V pastes the OS clipboard into the active pane when that pane is `ssh://`, `smb://`, or `mega://`. Today both layers reject it:

- `useFileOpDialogs.onPaste` returns "Paste is not available here" when `isRemotePath(activePath)`.
- `FileService.PasteClipboard` returns "paste is not available on remote connections" when `remote.IsRemote(dest)`.

Local paste stays `clipboard.PasteInto` → `filesystem.Copy` or a PNG write. Do not change that path.

In-app Copy and Move already use `runTransfer` (upload, download, within-host). Leave them alone.

## Behavior

Clipboard contents are what `internal/clipboard` already reads: a list of local files, or PNG bytes, or empty.

| Clipboard | Dest | Action |
| --------- | ---- | ------ |
| local files | remote dir | existing upload for that backend (`UploadCtx` on SSH, SMB, MEGA) |
| PNG bytes, no files | remote dir | write a temp PNG, upload that file, delete the temp |
| empty | remote | `clipboard.ErrEmpty` → UI already says "Nothing to paste" |
| anything | trash or archive | same errors as today (`rejectTrashDest`, `rejectArchiveWrite`) |

- Name for a PNG: `clipboard-YYYYMMDDHHMMSS.png`, then the same unique-name helper the remote upload already uses so an existing file is not overwritten.
- Directories on the clipboard upload as trees. `UploadCtx` already walks them. Do not flatten.
- One paste is one transfer job. Use `NewJobID` inside `PasteClipboard` (keep the current Wails signature: dest only) and the existing `transfer:progress` / `transfer:done` events. `transferStore.updateProgress` already creates a status-bar row from a job id it has not seen, so the bar appears without `startTransfer`.
- The frontend promise resolves when the upload finishes, then invalidates `['dir']` as it does for local paste. Do not invalidate `['dir']` on progress ticks.
- Cancel of that job uses the existing `CancelJob`. Wire the job into `storeJob` so cancel works. A cancelled paste must not leave a temp PNG on local disk.
- Cross-host rules stay inside upload: local files to one remote dest is the supported direction. If the clipboard somehow contains an `ssh://` path, return a clear error ("clipboard has a remote path; paste local files or images"). Do not try to download it. The OS clipboard does not produce those paths today.
- SMB and MEGA are in scope. They share the same guard and the same `UploadCtx` switch in `runTransfer`. Do not special-case SSH and leave SMB showing the old warning.

## Frontend

- Remove the `isRemotePath(activePath)` rejection in `onPaste`. Keep the trash and archive rejections.
- Success toast stays "Pasted". Errors stay `errMessage`.
- Do not add a second paste button.

## Tests

Go, no live server:

- A pure planner or a `PasteClipboard` with an upload func injected on the service: local paths + `ssh://` dest calls upload with those paths and does not call `filesystem.Copy`. If injection is awkward, extract `pasteMode(dest string, files []string, png []byte) (mode string, err error)` and table-test it: local dest + files → `local`, remote dest + files → `upload`, remote dest + png only → `upload-png`, remote dest + empty → empty error, trash dest → trash error, `ssh://` source path in the file list → error.
- Temp PNG: on upload error or cancel, the temp file is gone (test the cleanup func with a real temp file and a failing upload func).

Frontend: no new e2e against a real host. If `e2e/specs` already pastes into a local pane, leave that test green.

## Must not

- Change Copy so that it only fills a clipboard. Opposite-pane copy stays immediate.
- Write the PNG bytes through a string. Temp file, then upload, then delete.
- Hand-edit bindings. Signature of `PasteClipboard` stays `(dest string) error`, so bindings may not change. If you add a method, regenerate and leave bindings unstaged.

## Done when

- Paste of local clipboard files into an SSH, SMB, or MEGA directory uploads them and the status bar shows progress.
- Paste of a screenshot writes a uniquely named PNG on that remote.
- Local paste, trash paste, and archive paste behave as they do now.
- A failed or cancelled remote paste does not leave `clipboard-*.png` in the temp dir.
