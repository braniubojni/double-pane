# Spec: SSH and SMB soft delete V1

Status: draft
Out of scope: MEGA (already trash), a merged trash view that mixes OS trash with remote trash, undelete of files the server already purged, SMB recycle-bin admin shares (`$Recycle.Bin` version parsing — local Windows already has that in `trash_recycle_meta.go` and this spec does not reuse it for remote shares)

Cursor: implement this spec only. Read `internal/AGENTS.md` and `frontend/AGENTS.md` first.

## Current behavior

Local delete goes to the OS trash (`FileService.Delete` → `osTrash.Put`) and returns an undo token. The pane can open `trash://` (`filesystem.TrashURI`), restore (`RestoreTrash`), and empty.

Remote delete does not. `Delete` on an all-remote selection calls `remoteBackend.Delete` and returns an empty undo token. The dialog copy is "This cannot be undone." (`DeleteDialogs.tsx`), and `useFileOpDialogs` uses permanent delete when `isRemotePath(activePath)`.

- SSH: `Manager.Delete` → `removeAll` → `sftp.Remove` / recursive remove.
- SMB: `SMBManager.Delete` → `fs.RemoveAll`.
- MEGA: `MEGAManager.Delete` calls `sess.client.Delete(n, false)`, and the comment says MEGA trash. Leave MEGA on that path. Do not list MEGA trash in `trash://`.

Shift+Delete / `DeletePermanent` stays a real remove everywhere.

## Desired

SSH and SMB Delete moves the file aside on the **same host**, instead of unlinking it. Restore puts it back. Emptying remote trash permanently deletes those aside files.

Location, per session, created on first soft delete:

- SSH: `~/.double-pane-trash/<id>/` on that server. `id` is a UUID. A sibling `meta.json` in that folder stores JSON `{ "origin": "<absolute remote path>", "name": "<basename>", "deletedAt": "<RFC3339>" }`. The bytes live as `file` next to `meta.json` (a directory is moved as a tree named `file`).
- SMB: the same layout under `/.double-pane-trash/` on the **share** the file came from (not a server-wide path). A share root cannot be deleted (already rejected).

Use `Rename` / SFTP `Rename` and SMB rename when the aside directory is on the same volume. If rename fails across devices, copy then delete, and if the copy fails leave the original in place.

`FileService.Delete` for a same-scheme SSH or SMB selection returns a non-empty token, same as local, so the snack can offer Undo. Undo calls restore for those ids. The frontend permanent-path (`isRemotePath` forces `delPermanent`) must not run for a normal Delete on SSH/SMB. Shift+Delete still calls `DeletePermanent`, which keeps today's `Remove`.

Listing: do not overload `trash://` (that is the local OS trash). Each connection gets `ssh://user@host:port/.trash` and `smb://user@host:port/Share/.trash` as a virtual path `ListDir` understands — it lists aside entries as `FileEntry` with `Origin` set to the remote origin (the field already exists for local trash). The drives/connections UI does not need a new button if Go to / the path bar can open it; add a context-menu item "Remote trash" on an SSH or SMB pane `data-testid="menu-remote-trash"`.

`RestoreTrash` today is local. Add `FileService.RestoreRemote(paths []string) error` for those virtual rows, moving `file` back to `Origin`. Name collision: fail that row with "already exists", do not overwrite.

Empty: `FileService.EmptyRemoteTrash(root string) error` permanently `Delete`s the aside directory contents. Confirm dialog, same pattern as empty local trash.

MEGA `Delete` is unchanged.

## Tests

Fake SFTP or a temp-dir backend if one exists; otherwise test the path helper and meta JSON:

- soft delete records origin and does not leave the name in the source dir
- restore puts the name back
- restore when origin exists returns an error and leaves the aside copy
- `DeletePermanent` does not write meta
- MEGA still calls the client delete (no `.double-pane-trash`)

## Must not

- Put remote files into the local OS trash.
- Show remote aside files inside `trash://`.
